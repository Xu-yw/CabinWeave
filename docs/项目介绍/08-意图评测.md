# 意图评测

代码：
- `backend/evaluation/意图样本.json`：58 条样本。
- `backend/evaluation/evaluator.py`：样本校验、实验执行、指标计算和报告生成。
- `backend/evaluation/运行评测.py`：命令行入口。
- `backend/evaluation/报告/`：正式报告（`report.json`、`报告.md`）。
- `backend/core/intent_recognizer.py`：`use_keywords`、`use_llm` 构造参数，用来构造对照组。

## 1. 范围

只评意图识别，覆盖链路最前面的两层：快速通道和意图识别器。不做对话质量评测。

## 2. 样本

| 组 | 条数 | 构成 |
|---|---|---|
| 单意图 | 48 | 14 类每类至少 2 条，混入口语、省略和同音错字。按 Agent 分配：车控 15、导航 7、用车顾问 9、座舱助手 11、安全节点 6 |
| 多意图 | 10 | 2 个意图 7 条、3 个意图 3 条，其中串行 3 条 |

- 单意图里有 10 条易混与对抗样本：
  - 易混类别，如"空调不制冷了"标 fault_diagnosis、"空调现在开着吗"标 vehicle_status。
  - 像指令的问句和抱怨，如"车里温度有点高"，用来测快速通道不误命中。
  - 否定和假设句，如"差点追尾了，吓死我了""万一车着火了应该怎么办"，用来测紧急误报。
- 11 条是快速通道白名单内的单条简单指令，标 `fast_path: true`。
- 每条样本的字段：`id`、`text`、`intent`、`sub_tasks`（多意图时 2–4 项）、`execution`、`fast_path`、`note`（易混样本写标注理由）。
- 标注按 [意图识别](01-意图识别.md) 第 2 节的标注约定，不复用识别器 prompt 里的 31 条示例。样本定稿后不再修改，报告记录样本文件的 SHA-256，跑完不针对样本调规则。
- `load_samples` 校验格式：id 唯一、意图合法、多意图样本的子任务涉及至少 2 个意图且包含主意图、单意图样本只能是 parallel、多意图样本不标 `fast_path`。

## 3. 实验设计

| 实验 | 对比组 | 样本 | 做法 |
|---|---|---|---|
| E1 分层消融 | 只关键词 / 只 LLM / 关键词 + LLM | 58 条 | 只跑识别器。只关键词用 `use_llm=False`，结果等同 LLM 不可用；只 LLM 用 `use_keywords=False`，没有紧急直达和关键词兜底 |
| E2 快速通道 | 开 / 关 | ① 58 条<br>② 11 条 | ① 意图层面：关闭即 E1 的"关键词 + LLM"组；开启时被快速通道命中的样本改用规则对应的意图（只做规则匹配，不执行工具）<br>② 端到端：每次换一个用户（`eval:{id}:{on\|off}:{遍}`），也就是一辆套用 parked 场景的新车，调用 `orchestrator.run(req, fast_path=True/False)` |

- 调用模型的组各跑 3 遍；只关键词和快速通道匹配结果确定，跑 1 遍。
- 识别器和编排器内部的识别器都关闭缓存，全部串行执行，避免并发影响延迟。
- 识别耗时取识别器的 `latency_ms`（`time.perf_counter` 计时），端到端耗时只算 `orchestrator.run`，不含 HTTP 和记忆读写。

## 4. 指标

只算总体指标，不算逐类指标。

| 指标 | 定义 |
|---|---|
| 主意图准确率 | 58 条中主意图与标注一致的比例，3 遍取均值 |
| 多意图完全匹配率 | 10 条多意图样本中，子意图集合和执行方式都与标注一致的比例 |
| 快速通道覆盖率 | 标 `fast_path: true` 的样本中被命中的比例 |
| 快速通道误命中率 | 标 `fast_path: false` 的样本中被命中的比例 |
| 延迟 P50 / P95 | 最近秩法：排序后取第 ⌈p × n⌉ 个；3 遍的耗时合在一起算 |
| 状态一致率 | 同一条样本快速通道开、关两次执行后，`state_changes` 的字段和新值相同的比例 |

## 5. 结果

正式报告：2026-11-02，意图识别和其余角色都用 `deepseek-flash`，代码 `f5362af`（工作区无未提交改动），样本 SHA-256 `ed1344dda103…`。

**E1 分层消融**

| 组 | 主意图准确率 | 多意图完全匹配率 | 延迟 P50 | 延迟 P95 |
|---|---|---|---|---|
| 只关键词 | 79.3% | 70.0% | 0.18 ms | 0.31 ms |
| 只 LLM | 99.4% | 90.0% | 869.4 ms | 1.31 s |
| 关键词 + LLM | 98.3% | 90.0% | 839.6 ms | 1.19 s |

**E2 快速通道**

| 快速通道 | 主意图准确率 | 端到端延迟 P50 | 端到端延迟 P95 |
|---|---|---|---|
| 开 | 98.3% | 0.31 ms | 0.99 ms |
| 关 | 98.3% | 2.31 s | 3.23 s |

快速通道覆盖率 100%（11/11），误命中率 0%（0/47），状态一致率 100%（33 次比较）。

**分析**

- **准确率由 LLM 层决定**：只关键词 79.3%，加上 LLM 后 98.3%。只 LLM（99.4%）和分层只差 S25 一条：只 LLM 3 遍里错 1 遍，分层 3 遍都错。LLM 正常返回时两组最终采用的都是 LLM 的判断，这点差别来自模型输出的波动，不是关键词层造成的。
- **分层的价值在可用性和紧急响应**：
  - LLM 不可用时，只 LLM 的组会全部判为 other，分层还能靠关键词兜住 79.3%（即只关键词组的结果）。
  - 4 条紧急样本在分层组里全部由紧急短语直达，耗时约 0.4 ms；只 LLM 时要等约 0.9 s。
  - 其余样本两组都要调一次模型，延迟差异来自模型服务的波动。
- **只关键词的 12 条错例**分三类：
  - 词表没覆盖的说法，判为 other：转向手感、川菜馆、还能开多少公里、发微信。
  - 易混类别被判成字面意图：车窗和空调的状态问句被判成车控，"空调不制冷了"被判成空调控制，充电桩安装、车道居中辅助的用法问题被判成周边搜索和驾驶设置。
  - 否定和假设句被判成紧急求助："万一车着火了""差点追尾了"，以及"打不着火"（含"着火"）。这些都是词表打分误判，紧急短语本身没有误触发。
- **多意图**：关键词分句拆出的意图集合都对，但判断不了先后依赖，3 条串行样本都判成并行。LLM 能识别串行，只错 S58 一条：把"够的话去最近的商场"判成 navigation，标注约定里按类别找地点算 poi_search。
- **分层组的主意图错例只有 S25**："空调现在开着吗"3 遍都判成 climate_control，标注为 vehicle_status。
- **快速通道**：命中的 11 条在分层识别下本来也全对，所以开、关准确率相同。快速通道的收益在延迟：编排器耗时从秒级降到 1 ms 以内，命中时不调用模型。47 条不该命中的样本（含状态问句、抱怨句和多意图指令）一条都没命中。
- **执行结果一致**：11 条指令走快速通道和走完整链路（意图识别 + Agent 工具循环）改出的车辆状态，33 次比较全部相同。

## 6. 运行方式

在仓库根目录执行：

```bash
python backend/evaluation/运行评测.py
```

- 读取根目录 `.env` 的模型配置，`.env` 优先于进程里已有的同名环境变量（避免误用外层工具注入的 `ANTHROPIC_BASE_URL`）。不需要启动 Docker、Redis 或 ChromaDB。
- 可选参数：`--repeats N`（默认 3）、`--samples 路径`、`--skip-e2e`。全部实验约 500 次模型调用，串行执行约 6 分钟。
- 每次运行写到 `backend/evaluation/结果/<时间戳>/`（不提交）：`report.json` 记录配置、模型名、样本哈希、git 提交、指标、逐条预测和端到端记录，`报告.md` 是两张实验表和错例。正式一轮复制到 `backend/evaluation/报告/`。

## 7. 已知局限

- 样本是单人编写的合成数据，没有第二人独立标注；只有 58 条，一个样本约占 1.7 个百分点，98.3% 和 100% 只差 1 条。
- 端到端只测了白名单内的 11 条简单指令，状态一致率不代表完整链路在复杂指令上的执行正确率。
- 延迟受模型服务的时段波动影响；端到端延迟不含 HTTP 和记忆读写。
- 只用关键词时，否定、假设句和"打不着火"这类说法会被判成紧急求助；线上 LLM 正常时由 LLM 决定，不受影响。
