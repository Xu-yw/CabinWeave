# 快速通道

代码：`backend/core/fast_path.py`（匹配规则与播报模板）、`backend/agents/agent_orchestrator.py`（`try_fast_path`、通道统计）、`backend/api/main.py`（/chat 接入）、`backend/monitor/performance_monitor.py`（监控摘要）、`backend/tests/test_fast_path.py`（单元测试）。

## 1. 定位

"打开车窗""温度调到22度"这类简单指令，走完整链路至少要串行调 3 次模型（意图识别 1 次、Agent 工具循环 2 次）。快速通道用规则整句匹配这类指令，命中后直接调用工具、按模板播报，全程不调模型。

```
用户输入
 ├─ ① 快速通道：整句命中白名单 → 调用同一个工具函数（过安全规则）→ 模板播报      route = fast
 └─ ② 完整链路：记忆读取 → 意图识别 → 路由 → Agent 执行 → 汇总                route = slow
```

原则是宁可漏判，不能误判：拿不准的说法一律交给完整链路。

## 2. 匹配流程

`FastPath.match(message)` 依次检查，任意一步不通过即不命中：

1. 原文去掉空白后超过 20 字。
2. 全角转半角后含问号。
3. 用 `normalize_command` 归一化（全角转半角、去空格、小写、去口头词、中文数字转阿拉伯数字），再去掉首尾标点；中间还有标点或符号时不命中，比如"打开空调，关闭车窗"。两个数字之间的小数点除外，比如"22.5度"。
4. 含拒绝词，任意出现即不命中：

| 类别 | 词 |
|---|---|
| 连接词 | 然后、再、顺便、并且、同时、和、跟、还有、以及、接着、之后 |
| 疑问 | 吗、呢、么、怎么、为什么、多少、几、什么 |
| 否定 | 不、别、没、勿 |
| 指代或省略 | 它、这个、那个、刚才、还 |

5. 剩下的文本必须整句匹配白名单中某条规则的正则（`fullmatch`），按规则顺序取第一条。

第 1–4 步由 `reject_reason` 单独给出拒绝原因。例如"请帮我把副驾车窗打开吧。"归一化后是"把副驾车窗打开"，命中 F09；"打开空调和座椅加热"含"和"，不命中。

## 3. 白名单

| 规则 | 类别 | 说法示例 | 工具与参数 | 意图 |
|---|---|---|---|---|
| F01 | 空调开关 | 打开空调、开空调、把空调关了 | set_climate power | climate_control |
| F02 | 设定温度 | 温度调到22度、空调调到22.5度 | set_climate temperature | climate_control |
| F03 | 相对温度 | 温度调高两度、温度调低一点、调高温度 | set_climate temperature_delta（"一点"或不说幅度为 1 度） | climate_control |
| F04 | 设定风量 | 风量调到3档 | set_climate fan_level | climate_control |
| F05 | 相对风量 | 风大一点、风量调小一点、加大风量 | set_climate fan_delta（±1） | climate_control |
| F06 | 除雾 | 打开前挡除雾、关闭除霜 | set_climate defrost | climate_control |
| F07 | 座椅加热开关 | 打开主驾座椅加热、关闭副驾座椅加热 | set_climate seat_heat_zone + seat_heat_level（打开为 2 档、关闭为 0；不说位置为主驾） | climate_control |
| F08 | 座椅加热档位 | 座椅加热调到3档 | set_climate seat_heat_zone + seat_heat_level | climate_control |
| F09 | 车窗 | 关闭所有车窗、车窗开一半、车窗开到50%、打开后排车窗 | set_body part=window + action + zone（不说位置为主驾）+ open_percent（"一半"为 50） | body_control |
| F10 | 天窗 | 打开天窗 | set_body part=sunroof | body_control |
| F11 | 后备箱 | 打开后备箱、关闭尾门 | set_body part=trunk | body_control |
| F12 | 锁车 | 锁车、锁门、车门上锁 | set_body part=door_lock action=lock | body_control |
| F13 | 氛围灯 | 打开氛围灯 | set_lighting type=ambient | body_control |
| F14 | 双闪 | 打开双闪 | set_lighting type=hazard | body_control |
| F15 | 播放控制 | 播放、暂停、下一首、上一曲、切歌 | control_media action（不带 query） | media_control |
| F16 | 设定音量 | 音量调到15 | set_volume level | media_control |
| F17 | 相对音量 | 声音大一点、调小音量、大声点 | set_volume delta（±3） | media_control |
| F18 | 静音 | 静音、取消静音 | set_volume mute | media_control |

- agent_type 按 INTENT_AGENT 映射：F01–F14 为车控，F15–F18 为座舱助手。
- "温度高""风大""声音大"可能是抱怨，单独出现不算调节；要带"一点 / 点 / 些"，或带"调高 / 调大 / 加大"等动词。
- "空调开了"像在陈述状态，不算打开；关闭接受"关了"。
- 车窗开度要带 % 或说"一半"，超过 100 不命中。
- 带歌名或歌手的播放、解锁、导航、电话等都不在白名单里。

## 4. 执行与播报

编排器的 `try_fast_path(req)` 从工具注册表取同名工具，调用它的 handler。这和 Agent 调用的是同一个函数，所以同样经过车辆服务和安全规则 S01–S07。播报按工具结果生成：

| 工具结果 | 播报 |
|---|---|
| 被拒绝（blocked） | 拒绝原因，如"车辆行驶中不能打开后备箱，请停车后再试。" |
| 成功，触发调整类规则 S03 / S04 / S05 | 只播 notice，如"温度最高只能调到32度，已为你调到32度。" |
| 成功，其他情况 | "好的，…"模板 + notice（S07 提醒或空），如"好的，主驾座椅加热已调到2档。当前电量只剩12%，座椅加热会增加耗电，建议尽快充电。" |
| error、unsupported、handler 异常、工具未注册 | 视为未命中，回到完整链路 |

- 模板里的数值取执行后的实际值：先看 changes，没变化时读车辆状态。相对调节说的也是最终值，比如"风大一点"播"好的，风量已调到4档。"。
- 值没变（已经是该状态）时用同一模板。
- 播放时带上曲目标题，如"好的，正在播放每日推荐（示例曲库）。"。

命中时返回的 OrchestratorResult：

| 字段 | 内容 |
|---|---|
| route、fast_rule | "fast" 和命中的规则 ID |
| intent、agent_type、agent_types | 规则对应的意图和角色 |
| intent_result | confidence_level 为 high；sources 为 `decided_by=fast_path`、`fast_rule`、`llm_status=skipped` |
| tools_used、tool_traces | 一次工具调用，trace 格式和 Agent 的一致，tool_use_id 为 `fast-{request_id}` |
| state_changes、blocked_actions | 和 Agent 共用 `collect_vehicle_effects` 汇总 |
| routing_reason | 如 `route=fast, rule=F02` |

## 5. 接入位置

- **API 层**：`/chat` 在读取记忆之前先调 `try_fast_path`。命中时跳过记忆检索和偏好提炼，只把用户和助手两条消息写进对话记录，这样下一轮"再低一点"仍有上下文。未命中时走原流程，调用 `run(req, fast_path=False)`，不重复尝试。`ChatResponse` 增加 `route` 和 `fast_rule`。
- **CLI**：流程和 `/chat` 相同，每轮输出所走通道。
- **编排器**：`run(req, fast_path=True)` 入口也会先试一次，评测等直接调用 `run()` 的链路同样覆盖。

## 6. 可观测与开关

- **通道统计**：编排器累计两条通道的请求数和各规则命中次数，`get_route_stats()` 返回 `fast`、`slow`、`total`、`fast_ratio`、`rules`、`enabled`。完整链路里的网络兜底回复也计入 slow。监控摘要 `/monitor` 里的 `route_stats` 就是这份数据。
- **工具调用记录**：每条 trace 都带 `route` 和 `fast_rule`。
- **开关**：环境变量 `CABINWEAVE_FAST_PATH`，默认 on；off、0、false、no（不区分大小写）为关闭。运行中也可以直接改 `orchestrator.fast_path.enabled`。开、关两条通道的对比见 [意图评测](08-意图评测.md) 的 E2。

## 7. 已知局限

- 白名单只覆盖单条指令；"打开空调和座椅加热"这类多指令都交给完整链路，由多意图拆分处理。
- 快速通道不读对话上下文，"再高一点"这类依赖上一轮的说法会被拒绝词挡下，交给完整链路。
